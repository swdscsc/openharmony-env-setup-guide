# 面试问答：OpenHarmony 环境搭建

## Q1：为什么编译要放在 Linux，不能在 Windows 上编？

OpenHarmony 的构建系统（gn/ninja + hb）依赖 Linux 的工具链和文件系统特性；
官方也是在 Linux/Docker 环境里验证的。所以常见做法是 **Windows 编辑 + Linux 编译 + 主机烧录**，
也就是我这套环境的结构。

## Q2：为什么要用 Docker 编译容器，不直接装依赖？

依赖版本多、装起来容易和宿主机环境打架。用容器可以把编译环境固定成一个可复现的镜像，
换台机器拉同一个镜像就能编出一样的东西。本质上是**把环境本身当成可版本管理的产物**。

## Q3：hb 是什么？

OpenHarmony 的构建命令行工具：选择产品/板型配置后执行构建，产出可烧录的镜像。
对应到这次流程里，hb 负责编译，`mkimage.stm32` 负责把产物打包成开发板能识别的镜像格式。

## Q4：遇到"玄学报错"你怎么排查？

先分类，再逐项排除。我遇到过的三类基本覆盖了：
1. **路径类**：路径是否存在、大小写、有没有空格或中文、是 Windows 路径还是 Linux 路径
2. **权限类**：文件属主是谁、当前用户有没有读写执行权、挂载目录的权限映射
3. **环境变量类**：PATH 有没有写对、写进了哪个 shell 配置文件、有没有重新加载生效

从报错文本反推它属于哪一类，比盲目重试快得多。

## Q5：这套经历对你做别的嵌入式开发有什么用？

交叉编译的思路是通用的：**编辑在主机、编译在目标架构的工具链、产物烧到板子上跑**。
之后接触 ESP-IDF（ESP32）、STM32Cube 这类工具链，逻辑是同一套，只是工具不同。
我的几个项目（ESP32 姿态监测、STM32 充电监控）用的都是这个思路。
